Frontend projects tend to collect tools one at a time. Vite runs the development server, a separate bundler creates production output, another runner executes tests, and linting and formatting each bring their own commands and configuration. Then there is Node.js and the package manager to install and keep aligned across machines.

Vite+ is an attempt to bring that workflow under one roof. Its `vp` CLI connects Vite, Rolldown, Vitest, tsdown, Oxlint, Oxfmt, and Vite Task, and can also manage Node.js and package-manager versions. The aim is a coherent toolchain with shared commands and configuration, rather than a collection of unrelated tools.

This guide explains what Vite+ actually includes, how to get started, how its configuration and commands fit together, and what to review before migrating an established project. The key idea is that Vite+ provides a unified interface and compatible tools; it does not remove the need to understand your project's build, test, and package behavior.

## What is Vite+?

Vite+ has two related parts:

1. **The global `vp` CLI** is a standalone executable. It can manage Node.js and package-manager versions, install dependencies, run project tasks, and invoke the frontend toolchain. Its environment-management features do not require Node.js to be installed beforehand.
2. **The project-local `vite-plus` package** records a toolchain version in your project's manifest and lockfile. It contains the integrated frontend tools and a local `vp` binary, but relies on a Node.js runtime and package manager already being available.

You can use either on its own. A global install is optional; teams that want reproducible tool versions in each repository can install the local package and invoke it through their package manager, for example `pnpm exec vp check`.

### The tools behind the command

| Tool | Role in the toolchain |
| --- | --- |
| Vite | Development server and application build workflow |
| Rolldown | Bundler used by the Vite toolchain |
| Vitest | Test runner |
| tsdown | Library and package builds |
| Oxlint | Linting |
| Oxfmt | Formatting |
| Vite Task | Running and caching project tasks |
| `vp` environment tools | Managing Node.js and package-manager versions (global CLI) |

The benefit is not that each tool disappears. It is that a project can use one entry point and a more coordinated set of versions, commands, and configuration. Vite+ is most appealing when you already use several of these tools and want a simpler way to keep them working together.

## Install and start a project

If you want Vite+ available across projects, install the global CLI. The official installers are:

```bash
# macOS and Linux
curl -fsSL https://vite.plus | bash
```

```powershell
# Windows PowerShell
irm https://vite.plus/ps1 | iex
```

Open a new terminal after installation and check the available commands:

```bash
vp help
```

The global CLI can manage Node.js and package managers, but this behavior is optional. Use `vp env off` to prefer system-installed tools, or `vp env off node` and `vp env off pm` to disable one category.

For a new project, the usual flow is:

```bash
vp create
vp install
vp dev
```

`vp create` offers project templates for applications, packages, and monorepos. If you do not want a global CLI, you can create a project through your package manager, for example:

```bash
pnpm create vite-plus
```

For a project-local installation, run the binary through the package manager, such as `pnpm exec vp dev`. That keeps the toolchain version tied to the repository rather than whichever global version is installed on a developer's machine.

## The everyday workflow

Once the project is set up, the common commands cover the path from local development to a production artifact:

```bash
vp dev       # Start the Vite development server
vp check     # Run formatting, lint, and type checks
vp test      # Run tests with Vitest
vp build     # Build an application
vp preview   # Preview an application build locally
vp pack      # Build a library or package
```

The `vp check` command brings together formatting, linting, and type checking. You can also run individual checks with `vp fmt` and `vp lint`. Use `vp test` for the Vitest runner, `vp build` for application builds, and `vp pack` for libraries.

Vite+ also includes package-management commands (`vp add`, `vp remove`, `vp update`, and `vp install`) and a task command for running project scripts and workspace tasks. Built-in commands such as `vp build` have fixed meanings. To run a script declared in `package.json`, use:

```bash
vp run my-script
```

This distinction matters when migrating: an existing script named `build` will not redefine the built-in `vp build` command. Use `vp run build` if you specifically need to invoke that package script.

In a monorepo, `vp run` can coordinate tasks across workspace packages and cache results. This can cut repeated work in CI or local development, but caching only helps when task inputs and outputs describe the work correctly. Teams still need to review what each task reads and writes.

## Configuration in `vite.config.ts`

Vite+ uses `vite.config.ts` as a central place to configure the integrated toolchain. This gives developers one familiar configuration entry point, while the tools still have their own options and semantics. A simplified example might look like this:

```ts
import { defineConfig } from 'vite-plus'

export default defineConfig({
  // Vite application and plugin configuration
  plugins: [],

  // Test runner settings
  test: {
    // Vitest configuration
  },

  // Package build settings
  pack: {
    // tsdown configuration
  },
})
```

This illustrates the shape, not a complete production config. Use the official configuration reference for the supported fields and the relevant tool documentation for detailed options. Centralization makes the toolchain easier to discover; it does not make every configuration interchangeable or mean that every project needs a `pack` section.

## Migrating an existing project

For an existing Vite project, `vp migrate` is the starting point. It can update dependencies, rewrite supported imports, combine tool configuration, update scripts, and optionally set up editor integration, agent instructions, and Git hooks. A monorepo migration must run from the workspace root because package-manager configuration and lockfiles are shared.

Migration is an automated edit, not a guarantee that your project is behaviorally unchanged. Some work will still require review, especially when a project has custom Vite plugins, test setup, package exports, lint rules, or library-build behavior.

### Prepare before running the migrator

1. **Inspect the project and worktree.** Identify the package manager, scripts, Vite and Vitest versions, configuration files, and any local edits. Keep unrelated changes intact.
2. **Meet the prerequisites.** For a project not already on Vite+, first upgrade to Vite 7 or later and Vitest 4 or later when needed. Resolve those upgrades before beginning the Vite+ migration.
3. **Keep the original install available.** Do not replace the old lockfile or dependencies before migration. The migrator uses the installed/original Vitest version to determine compatibility work.
4. **Use the intended target CLI.** Check its migration help, and run from the workspace root. Automated environments can use `--no-interactive`.

For example, with a global CLI:

```bash
vp help migrate
vp migrate --no-interactive
```

With no global CLI, invoke the target `vite-plus` version through `pnpm dlx` or `npx` as shown in the Vite+ migration guide. Do not use an old project's `node_modules/.bin/vp` to migrate that same project.

Afterward, review every changed manifest, lockfile, script, import, and configuration file. Resolve migration blockers and examine every review warning even if the command exits successfully. Then install and validate the project:

```bash
vp install
vp check
vp test
vp build  # use vp pack for a library
```

The migration is designed to be repeatable, but a second run is not a substitute for reviewing the first diff and the migrator's report.

### Vitest 5: check behavior, not just imports

Vite+ 1.0 uses Vitest 5. Before a project reaches that version, the migration flow expects the source project to be on Vitest 4 and preserves compatibility settings where behavior changed. Keep these generated settings for the first validation run; remove them only after checking the tests that depend on the old behavior.

For example, Vitest 5 enables `clearMocks` by default. It clears mock call history before each test while leaving mock implementations intact. If a test relied on calls made in setup or in a previous test, its assertions may now change. Other compatibility review areas include shared Vite server initialization, browser locator matching, coverage thresholds, and fake timers.

The Vite+ compatibility guide is useful alongside the upstream Vitest migration guide. Read both before removing generated compatibility settings. A successful dependency update alone does not tell you whether your tests still assert the same behavior.

### tsdown 0.23: review package builds

Vite+ also adopts tsdown 0.23 for package builds. The release changes several options and defaults. Common renames include `bundle: false` to `unbundle: true`, `outExtension` to `outExtensions`, `publicDir` to `copy`, and `removeNodeProtocol: true` to `nodeProtocol: 'strip'`. The dependency option `skipNodeModulesBundle: true` becomes `deps.neverBundle: true`.

There are behavioral changes too: `deps.resolveDepSubpath` defaults to `false`, and the Are The Types Wrong profile defaults to `esm-only` instead of `strict`. If you need prior behavior, set the corresponding option explicitly. For API users, the return shape of `build()` changes to `{ bundles, watch }`.

The Vite+ migrator updates supported static pack configurations and can add compatibility settings for older or unknown tsdown versions. Inspect those comments and your package's public exports, then run `vp pack` and test the package as a consumer would. Applications that do not publish packages may not use this part of the toolchain at all.

## What Vite+ changes—and what it does not

The practical change is a consolidated interface: one CLI can handle development, checks, tests, builds, package tasks, and optionally runtime and package-manager setup. A unified toolchain can also make it easier for contributors to use the same versions and commands locally and in CI.

But Vite+ does not make migration risk-free, guarantee that every project-specific configuration is supported, or replace the need to understand each tool's behavior. It is a good fit when the included defaults match your workflow and you value shared commands. If your project depends on specialized tooling, custom build pipelines, or a carefully tuned test setup, evaluate those pieces individually before adopting the full toolchain.

Start with the parts you need. You can use the global CLI for environment or task management without adopting the local frontend package, and a project can pin the local `vite-plus` package when reproducibility matters. The useful question is not whether one CLI can replace every tool in a repository; it is whether Vite+'s integrated workflow makes your actual project easier to maintain.
